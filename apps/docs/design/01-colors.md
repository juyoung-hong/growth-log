# 컬러 시스템

**원천 파일**: [`apps/frontend/src/app/styles/theme.css`](../../frontend/src/app/styles/theme.css)

## 왜 이렇게 만들었나

Toss Design System(TDS)의 색 체계 — 한 색을 50~900의 10단계로 두고, 화면에서는 항상 이 단계 이름으로만 색을 고르는 방식 — 을 참고했다. 다만 TDS의 실제 색값(hex)은 상업 라이선스라 그대로 가져다 쓸 수 없다.

그래서 **구조는 TDS를 참고하되, 값은 [Open Color](https://yeun.github.io/open-color/) v1.9.1(MIT License)에서 가져왔다.** 규칙(체계·용법)과 표현(색값)을 분리했기 때문에, 이 문서에 실린 값은 다른 프로젝트에 옮겨써도 라이선스 문제가 없다.

## 팔레트 매핑

Open Color의 색 이름 그대로 쓰지 않고, TDS와 이름을 맞춘 것이 셋 있다.

| 이 시스템의 이름 | Open Color 원본 이름 |
|---|---|
| `grey` | `gray` |
| `purple` | `grape` |
| 나머지 10색 | 이름 동일 |

Open Color는 각 색상당 인덱스 `0~9`(10단계)를 제공한다. 이걸 `50, 100, 200, …, 900`에 순서대로 대응시켰다 — 인덱스 0이 `50`, 인덱스 1이 `100`, 이후로는 인덱스와 백단위가 그대로 맞아떨어진다(인덱스 5 = `500`).

## 사용 규칙

### 1. Tailwind 기본 팔레트는 지운다

```css
@theme {
  --color-*: initial;
  --color-white: #ffffff;
  --color-black: #000000;
  /* ...이 팔레트만 등록 */
}
```

Tailwind CSS가 기본 제공하는 `slate`·`indigo`·`emerald` 같은 팔레트를 남겨두면, 이 시스템에 정의하지 않은 단계(예: `red-100`을 빼먹었을 때)를 실수로 써도 **Tailwind 기본색이 조용히 나온다.** 이 리셋을 해두면 정의 안 된 색을 쓰는 순간 해당 유틸리티 클래스 자체가 생성되지 않아, 빌드 결과물에서 바로 드러난다.

### 2. 팔레트 단계로만 색을 쓴다

컴포넌트 코드에 `#3182f6` 같은 리터럴 hex를 직접 쓰지 않는다. 항상 `bg-blue-800`, `text-grey-700`처럼 **팔레트 토큰**을 통해서만 색을 지정한다. 새 의미 색이 필요하면 팔레트에서 고르고, 팔레트에 없는 색이 필요하면 팔레트를 먼저 확장한다(2.3절 방식 그대로).

### 3. 의미 색(semantic token)은 팔레트 값을 참조한다

업무 개념에 따라 이름 붙인 토큰은 항상 팔레트 변수를 `var()`로 참조하지, 직접 hex를 적지 않는다.

```css
--color-status-progress-bg: var(--color-blue-100);
--color-status-progress-fg: var(--color-blue-900);
```

이렇게 하면 나중에 팔레트 자체(예: blue 색상표)를 바꿔도 의미 색 쪽 코드는 손댈 필요가 없다.

### 4. weak 어법 — 배경 100단계 + 같은 계열 900단계 글자

TDS Badge의 "weak" 표현(연한 배경 + 같은 계열의 진한 글자)을 이 시스템 전체의 의미 색 공식으로 채택했다.

```
배경: 그 색의 100단계
글자: 같은 색의 900단계
```

새로운 상태·구분 색이 필요할 때도 이 공식을 그대로 따른다.

## 접근성 — 원칙 우선, 예외 없음

각 조합의 배경/글자는 [WCAG 2.1 명도 대비](https://www.w3.org/TR/WCAG21/#contrast-minimum) 기준(본문 텍스트 4.5:1)으로 실측했다. Open Color는 TDS보다 전반적으로 밝은 팔레트라, 같은 4.5:1을 만족하려면 TDS에서 500단계로 충분하던 자리가 대부분 700~900단계까지 내려간다.

**green·yellow는 900단계로도 4.5:1을 못 채운다.** 이 두 색만 규칙을 바꿔(예: 어두운 회색 글자로 대체) 대비를 억지로 맞추는 방법도 있었지만, 채택하지 않았다. 색마다 규칙이 갈리면 "이 색은 왜 다르지"를 매번 따져야 하는 비용이, 낮은 대비 수치 하나보다 크다고 판단했기 때문이다.

| 조합 | 명도 대비비 | 판정 |
|---|---|---|
| `bg-green-100` / `text-green-900` (weak) | 3.81 | AA 미달 |
| `bg-yellow-100` / `text-yellow-900` (weak) | 2.69 | AA 미달 |
| `bg-green-900` / `text-white` (fill) | 4.37 | AA 미달 |
| `bg-yellow-900` / `text-white` (fill) | 3.00 | AA 미달 |

**대비가 실제 문제가 되는 자리는 규칙을 억지로 구부리지 않고, 그 자리에 맞는 다른 색을 새로 고른다.** 예를 들어 저장공간 사용량 경고 배너는 원래 "보류(hold)" 상태 색(yellow)을 그대로 재사용하고 있었는데, 두 개념(작업의 보류 상태 vs 용량 경고)이 다른데도 같은 토큰을 썼던 게 문제였다. 별도 토큰 `--color-warning-*`을 새로 만들고 orange를 배정해 분리했다 — orange도 완전한 AA는 아니지만(3.62:1) yellow(2.69:1)보다는 낫고, 무엇보다 "보류 상태 배지 색을 바꾸면 경고 배너도 같이 바뀌는" 결합을 없앴다.

```css
/* 저장공간 사용량 경고는 태스크 '보류' 상태와 다른 개념이다.
   별도 토큰으로 분리해, 하나를 바꿔도 다른 하나가 영향받지 않게 한다. */
--color-warning-bg: var(--color-orange-100);
--color-warning-fg: var(--color-orange-900);
```

## 다크 모드

이번 범위에서 다크 모드 화면을 만들지는 않지만, `.dark` 클래스가 켜졌을 때 shadcn 기본 회색이 튀어나오지 않도록 같은 팔레트로 최소한의 짝을 맞춰 뒀다(`theme.css`의 `.dark` 블록). 실제 다크 모드를 구현할 때는 이 문서의 대비 원칙을 다크 배경 기준으로 다시 계산해야 한다 — 지금 값은 자리만 채운 것이다.

## 다른 프로젝트에서 재사용하는 방법

1. [Open Color 저장소](https://github.com/yeun/open-color)에서 `open-color.json`(또는 원하는 버전)을 받는다.
2. 이 문서의 "팔레트 매핑" 표대로 색 이름을 맞추고, 인덱스 0~9를 50~900에 대응시켜 `@theme` 블록에 등록한다.
3. `--color-*: initial`로 프레임워크 기본 팔레트를 지운다.
4. 의미 색은 항상 `var(--color-{hue}-{step})`로 참조하고, weak 어법(100 배경 + 900 글자)을 기본 공식으로 삼는다.
5. 각 조합의 실측 대비비를 계산해 코드 주석에 남긴다. AA에 못 미치는 조합이 생기면, 색을 바꿀지 원칙을 지킬지 그 자리에서 판단하고 **판단 근거를 주석에 남긴다** — 이 프로젝트가 택한 기준(색상 간 규칙 일관성 > 개별 조합의 AA 통과)을 그대로 따를 필요는 없지만, 판단을 명시적으로 남기는 습관은 유지한다.
